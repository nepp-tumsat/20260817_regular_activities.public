Webのしくみ

今日作るのは、ブラウザだけで動く小さなWebページです。Claude Code が書いたコードを読むとき、どのファイルが何を担当しているかが分かっていると、指示がぐっと的確になります。まずそこだけ押さえます。

ブラウザが受け取るのは、結局この3つ

🧱

HTML

ページに何があるか。見出し、文章、ボタン、入力欄といった中身と構造。

骨組み
🎨

CSS

どう見えるか。色、大きさ、余白、並べ方。中身は変えず、見た目だけを決める。

見た目
⚙️

JavaScript

どう動くか。押されたら反応する、データを保存する、表示を書き換える。

動き
家にたとえるとHTML が間取りと壁、CSS が内装と色、JavaScript が電気やスイッチ。HTMLだけでも家として成立しますが、CSSがないと真っ白で、JSがないとスイッチが効きません。
「Webページ = この3ファイル」ではありません実際の開発では React や Next.js のようなフレームワークを使い、これらは自動生成されることのほうが多いです(サークルの通常開発もそちら)。サーバー側でHTMLを組み立てて返す作り方もあります。
ただしどの作り方をしても、最後にブラウザが受け取るのは HTML / CSS / JavaScript という点は変わりません。今日はその中間層を省いて、3つを直接書きます。ここが分かっていれば、フレームワークを使い始めたときも「結局これが生成されている」と読み替えられます。

同じボタンを、3段階で作ってみる

① HTML だけ — ボタンは出るが、飾りっ気がなく押しても何も起きない。

<button id="post">空いてる</button>

② CSS を足す — 見た目が付く。動きはまだない。

#post {
  background: #1f6e54;
  color: white;
  padding: 10px 20px;
  border-radius: 6px;
}

③ JavaScript を足す — 押すと反応するようになる。

document.getElementById("post").addEventListener("click", () => {
  alert("投稿しました");
});

この3つは別々のファイルに分けても、1つのファイルにまとめても動きます。今日はチームで分担するので、機能ごとにファイルを分けます(セットアップと開発タブの「チーム開発の作法」)。

ブラウザは上から順に読んでいるだけ

1

HTMLを読む

ページに何があるかを組み立てる

2

CSSを適用

読み込んだCSSで見た目を決める

3

JSを実行

書かれた処理を上から実行する

4

操作を待つ

クリックなどが起きたらJSが反応する

だから今日の構成なら、ブラウザで index.html を開くだけでページは動きます。サーバーもビルドも要りません。ファイルを保存して、ブラウザを再読み込みするだけです(フレームワークを使う場合は、この前にビルドという変換工程が挟まります)。

デバッグの入口思ったとおりに動かないときは、ブラウザで右クリック → 検証(または F12)を開いてください。Console タブにJavaScriptのエラーが赤字で出ています。そのエラー文をそのまま Claude Code に貼るのが一番速い直し方です。

フロントエンドとバックエンド

Webアプリはたいてい、手元のブラウザで動く部分と向こう側のサーバーで動く部分に分かれています。HTML / CSS / JavaScript は、このうち前者です。

🖥 フロントエンド= あなたのブラウザの中で動く
  • HTML / CSS / JavaScript
  • 画面の表示、ボタンの反応
  • 入力チェック(親切のため)
中身は誰でも見られる
インターネット リクエスト → ← レスポンス
🗄 バックエンド= 向こう側のサーバーで動く
  • データベース(全員ぶんのデータ)
  • APIキー・パスワードなどの秘密
  • 本当の判定・計算
中身は見えない

この「見える / 見えない」の差がすべての出発点です。 フロントエンドのコードは、ブラウザに届いた時点で全部読めます(右クリック → 検証 で誰でも中身を見られます)。だからバックエンドを分ける理由は、突き詰めると次の3つです。

  1. 秘密を置く場所がいる — APIキーやパスワードをフロントに書くと、置いた瞬間に公開されます
  2. みんなでデータを共有する — ブラウザに保存したデータはその人のそのブラウザにしか存在しません。他の人と共有するにはサーバーが要ります
  3. フロントは信用できない — ブラウザ側のコードは書き換えられます。「会員は500円」の判定をフロントだけでやると、いくらでも改ざんできます
今日は「バックエンドなし」で作りますデータは localStorage(そのブラウザの中)に保存します。サーバーもデータベースも用意しないので、他の人とデータは共有されません。
これは手抜きではなく、85分で動くものに着地させるための設計判断です。サークルの本格的な開発ではバックエンド(Go / Python / Node など)を用意します。
お題を決めるときに効いてくる話「みんなで情報を出し合う」系のアイデアは、本来バックエンドがないと成立しません。今日は1台のブラウザの中でデモが成立すればOK(自分で投稿 → 一覧に出る、まで動けば成果)と割り切って設計してください。共有まで本気でやりたいなら、それは9月のハッカソンの題材です。

URL のしくみ

URL は「インターネット上のどこにある何を、どうやって取りに行くか」を1行で書いたものです。分解するとこうなっています。

https://スキーム取りに行く方法。
s = 通信が暗号化されている
nepp-tumsat.github.ioホストどのサーバーか。
いわば住所
/20260817_regular_activities.public/パスサーバーの中のどこか。
フォルダとファイルの場所
?q=lunchクエリ付け足しの情報。
検索語や条件を渡す
(このページには付いていません)
#webフラグメントページ内のどこか。
サーバーには送られない

ホストとパスは、いま見ているこのページの実物です(クエリだけ例として足しています)。タブを切り替えると末尾の #web の部分が変わりますが、ページ自体は読み込み直されていません。フラグメントはサーバーに送られず、ブラウザの中だけで使われるからです。

よく出てくる形意味
file:///Users/…/index.html自分のPCのファイルを直接開いている。今日の開発中はこれ
http://localhost:3000自分のPCの中で動かしているサーバー。3000 はポート番号(何番の窓口か)
https://example.com/末尾がフォルダのときは、その中の index.html が自動で開かれる
https://example.com/menu?date=today? 以降がクエリ。「date は today」という情報をサーバーに渡している
まとめ
  • HTML = 何があるか / CSS = どう見えるか / JavaScript = どう動くか
  • フロントエンド(ブラウザ側)は中身が全部見える。だから秘密と共有データはバックエンド(サーバー側)に置く
  • 今日はバックエンドなし。データは localStorage で、他の人とは共有されない
  • フレームワークを使っても、ブラウザが最後に受け取るのはこの3つ。今日は直接書くだけ
  • ブラウザは上から順に読んで実行しているだけ。今日の構成なら index.html を開けば動く
  • 動かないときは検証 → Console のエラーを Claude Code に貼る
  • URL は スキーム / ホスト / パス / クエリ / フラグメント でできている

APIと課金の仕組み

今日は「APIキー」を配られました。これが何で、なぜ人に見せてはいけないのか、そしてなぜ使うほどお金がかかるのかを押さえておきます。自分たちのアプリで外部サービスを使うときにも、そのまま効く話です。

API =「他人が作った機能を、自分のプログラムから呼ぶ窓口」

人間がブラウザで使う画面がある一方で、プログラムから呼ぶための入口が別に用意されていることがあります。それが API です。

1

リクエスト

自分のプログラムが「これして」と送る。ここにAPIキーを添える

2

認証

相手のサーバーがキーを見て「誰の依頼か」を確認する

3

処理

相手のサーバーが実行する。自分のPCではない

4

レスポンス + 記録

結果が返る。同時に「誰がどれだけ使ったか」が記録される

APIキー = 会員証 兼 請求書の宛名キーは「誰が呼んだか」を示すものです。つまりキーを持っている人は、あなたの名前で使えて、あなたに請求が飛びます。パスワードと同じ扱いをしてください。

サブスクと従量課金の違い

サブスク(Claude Pro / Max など)API(従量課金)
支払い月額固定。使っても使わなくても同じ使った分だけ。使わなければ $0
使いすぎたら一定時間使えなくなる。追加請求はないそのぶん金額が増える。上限は自分で設定する
誰が使う想定人間が画面から使うプログラムから呼ぶ
向いているもの毎日たくさん使う個人自分のアプリに組み込む / チームで配る

Claude Code はどちらでも動きます。今日は全員に同じ環境を用意するためにAPIキー方式にしています。一方で、自分が作ったアプリからAIや外部サービスを呼ぶときは、ほぼ必ずAPIキー方式になります。

トークンと料金:なぜ会話が長いと高くなるのか

AIのAPIは「文字数」ではなくトークンという単位で数えます。日本語ならおおよそ1文字が1トークン前後です。

  • 入力トークン(こちらが送った分)と出力トークン(返ってきた分)で単価が違い、出力のほうが高い
  • AIは会話を覚えていないので、毎回これまでの会話全部を送り直しています。だから会話が長くなるほど1回あたりの入力が増える
  • 同じ内容を繰り返し送る部分は割引される仕組み(キャッシュ)があるので、実際の請求は素直な掛け算より安くなります
だから /clear が効く話題が大きく変わったら /clear で履歴をリセットすると、送り直す量が減って安く・速くなります。逆に、関係ない長い会話を引きずったまま作業を続けるのが一番もったいないパターンです。/cost で今いくら使ったかをいつでも確認できます。

自分たちのアプリでAPIを使うときの注意

APIキーをフロントエンドのコードに書かないブラウザで動くJavaScriptに書いたキーは、ページを開いた全員に丸見えです(検証ツールで誰でも読めます)。「見えないところに置いたつもり」でも、ブラウザに届いた時点で公開されています。

キーを安全に使うには、キーを持つサーバーを自分側に用意して、ブラウザ → 自分のサーバー → 外部API と中継する必要があります。今日はそこまで作る時間はありません。なので、外部APIを使いたい場合は次のどちらかにしてください。

  • キーが要らない公開APIを選ぶ — 天気、路線、公共データなど。今日はこちらを強く推奨
  • そもそも外部APIを使わない — データはブラウザに保存(localStorage)するだけでも、ちゃんと動くものは作れます
まとめ
  • API — プログラムから機能を呼ぶ窓口。処理は相手のサーバーで動く
  • APIキー — 会員証であり請求書の宛名。漏れたら他人が自分の名前で使える
  • サブスク vs 従量課金 — 月額固定か、使った分だけか。アプリに組み込むなら後者
  • トークン — 会話全部が毎回送られる。長引くほど高い。/clear と /cost を使う
  • フロントにキーを書かない — ブラウザに届いた時点で公開。今日はキー不要のAPIを選ぶ

アイデアの出し方

良いアイデアは「思いつく」ものではなく、具体的な誰かの、具体的な困りごとから逆算するものです。この4ステップで、今日の85分で作れるサイズまで削り込みます。

STEP 1

ペルソナ

誰の話か。「大学生」ではなく、実在しそうな1人に絞る

STEP 2

課題の具体化

その人が、いつ・どこで・何回・どうなって困るのか

STEP 3

市場調査

今その人はどうしのいでいるか。既存の何が足りないのか

STEP 4

MVP

その課題が解ける最小の形に削る

以下、「学食が混んでいる」という題材で 1 → 4 を通してやってみます。

STEP 1 — ペルソナ:「大学生」ではなく「田中さん」にする

「大学生向けのアプリ」だと、何を作っても正解に見えて、結局なにも決まりません。実在しそうな1人まで絞ると、機能を入れるか外すかがその場で決められます。

🧑‍🎓

田中さん(2年)

時間割
火曜は2限が2号館、3限が大教室。移動に8分かかる
お金
学食は安いので週4で使いたい。外食は厳しい
性格
人に聞くのが少し面倒。スマホは常に見ている

「席を探して歩き回るくらいなら、もう購買でいいかなってなる」

今日のペルソナは「自分」か「隣の人」でいい本来はインタビューして作りますが、今日は時間が限られています。チームの誰かが実際に困っていることを題材にするのが一番速く、しかも精度が高いです。

STEP 2 — 課題の具体化:「不便」で止めない

課題がぼんやりしていると、解決策もぼんやりします。いつ・どこで・何回・どうなるかまで書けたら、解くべきものは自動的に見えてきます。

✗ ぼんやり 学食が混んでいて不便
✓ 具体的 田中さんは12:15に学食へ着くが席がなく、5〜10分探し回る。見つからないと購買のパンを買って教室で食べることになり、週に2〜3回そうなっている。

左は「で、何を作る?」に答えられません。右は「着く前に空席が分かればいい」がすぐ出てきます。

STEP 3 — 市場調査:5分だけ「もう誰かが解いてないか」を調べる

既にあるものを作り直すのも学びとしてはアリですが、「なぜ既存では足りないのか」を1行で言えると、作るものが一気にシャープになります。

今ある手段できること足りないこと
大学の公式サイトメニューと営業時間が分かる混雑状況は載っていない
Google Maps の混雑度建物単位のざっくりした混み具合席が空いているかは分からない。反映が遅い
友達に LINE で聞く正確相手が返信するまで分からない

この表から、空いているところが1行で書けます。

結論(=作る理由)リアルタイムに・席単位で・誰にも聞かずに分かる手段が存在しない。
5分ルール検索して3つ見たら終わりにしてください。市場調査は無限にできてしまい、「調べていたら開発時間がなくなった」が今日いちばん多い失敗です。深掘りは動くものができた後で。

STEP 4 — MVP:その課題が解ける最小の形に削る

MVP(Minimum Viable Product)= 最小限だけど、ちゃんと価値が出る形。 パーツを順番に作っていくと最後まで誰も使えませんが、MVPから育てると最初から使えます。

✗ パーツから作る 🛞タイヤ → 🔩車体 → 🚗完成 完成するまで誰も移動できない。時間切れ = 何も残らない
✓ MVPから育てる 🛹スケボー → 🛴キックボード → 🚲自転車 → 🚗車 どの段階でも「移動できる」。時間切れでも成果が残り、途中で改善もできる

今日は開発85分です。まずスケボーを作りきってから、余った時間でキックボードに伸ばすと考えてください。学食の例で削ると、こうなります。

✗ 全部乗せ
  • ログイン機能
  • 座席マップ
  • 空席になったら通知
  • AIによる混雑予測
  • 過去の統計グラフ
✓ MVP(スケボー) 「空いてる / 混んでる」の2択ボタンを押すと記録され、直近15分の記録が一覧で出る。
それだけ。

右は田中さんの課題(着く前に分かりたい)をちゃんと解いています。左の機能は1つも足さなくても解けるので、まずは作りません。

ただし、本当に「みんなで共有」するにはバックエンドが要ります今日は localStorage しか使わないので、投稿は自分のブラウザの中にしか残りません(Webのしくみタブ参照)。
今日のゴールは1台で「投稿する → 一覧に出る」が動くことです。そこまで動けば、あとはデータの置き場所をサーバーに替えるだけ、という状態になります。成果シェアではそう説明してください。

MVPに削るときの判断基準

  • 「これがないと課題が解決しない」機能だけ残す。 「あったら便利」は全部あとまわし

  • デザインは後回し。 動くのが先。見た目は余った時間で
  • 成果シェアで見せる1画面を先に決める。 その画面に必要なものだけ作る

  • ペルソナ — 「大学生」ではなく「田中さん」。今日はチームの誰かが実際に困っていることでいい
  • 課題 — いつ・どこで・何回・どうなるかまで書く
  • 市場調査 — 5分。既存3つを見て「足りないこと」を1行で

セットアップ

チームに配られたAPIキーで Claude Code を使えるようにします。所要5分。Step 1 のインストールは時間がかかるので、先に走らせてから話を聞いてください。

個人で Claude Pro / Max を契約済みの人へ普段の自分のログインのまま参加してOKです。キーの受け取りと Step 2 は不要なので、このタブ後半の「チーム開発の作法」へ進んでください。
作業環境macOS のターミナル、または Windows の WSL(Ubuntu など)で作業します。Windows の人は PowerShell やコマンドプロンプトではなく WSL のターミナルを開いてください。WSL がまだ入っていない人は導入に時間がかかるので、運営に声をかけてください。

VS Code の統合ターミナルで動かすのがおすすめ

Claude Code は普通のターミナルだけでも動きますが、VS Code でプロジェクトを開き、その中のターミナルで claude を起動すると、AIが書き換えたファイルが目の前で変わるのが見えます。今日のように「AIが何をしたのか」を理解しながら進めたい場面ではこちらが圧倒的に分かりやすいです。

  1. VS Code で作業フォルダを開く(ファイル → フォルダーを開く)
  2. Ctrl + ` (macOS も同じ)で統合ターミナルを開く
  3. そのターミナルで、下の Step 1〜3 をそのまま実行する

左のファイル一覧が Claude Code の作業に合わせて増えていくので、HTML / CSS / JS の役割を実物で確認できます。index.html を右クリック → ブラウザで開けば、その場で動作確認もできます。

Windows(WSL)の人はフォルダの開き方に注意VS Code に WSL 拡張を入れ、左下の緑のボタンから 「WSL への接続」→ WSL 側のフォルダを開いてください。Windows 側(C:\ 配下)のフォルダを開くと、動作が極端に遅くなったり claude が見つからなかったりします。左下に WSL: Ubuntu と出ていれば正解です。
拡張機能は今日は不要Claude Code の VS Code 拡張もありますが、今日は統合ターミナルで十分です。APIキーを環境変数で渡す都合上、ターミナルから起動するほうがトラブりません。

  1. Claude Code をインストールする

    すでに入っている人は飛ばしてください(claude --version で確認できます)。

    curl -fsSL https://claude.ai/install.sh | bash

    WSL で curl: command not found と出たら、先に curl を入れてから再実行してください。

    sudo apt update && sudo apt install -y curl

  2. チームのAPIキーを環境変数にセットする

    チームリーダーから受け取ったキー(sk-ant-api03-…)を貼り付けます。

    export ANTHROPIC_API_KEY="sk-ant-api03-..."

    ターミナルを開き直すと消えるので、その場合はもう一度実行してください。

  3. 起動して初期設定をする

    mkdir hands-on && cd hands-on
claude
    1. 「このAPIキーを使用するか」と聞かれたら Yes を選ぶ
    2. /model と入力して Sonnet を選択(今日はSonnetで進めます)
    3. 疎通確認として軽い指示を1回:「このフォルダに hello.txt を作って」

    hello.txt ができたらセットアップ完了です 🎉

覚えておくと便利なコマンド

Consoleアカウントで「ログイン」しないでくださいログイン画面が出ても、Console(platform.claude.com)のアカウントでのサインインは選ばず、必ずAPIキー(環境変数)を使ってください。今日はチームに配られたキーで動かします。
キーの取り扱い
  • git にコミットしない(コード内に書かず、環境変数のままにする)
  • スクリーンショット・配信画面に写さない
  • チーム外に共有しない
なぜこれが大事なのかはAPIと課金タブを読むと腑に落ちます。
  • キーはイベント終了時に失効します。持ち帰っても使えません。
  • 途中で応答が返ってこなくなったら、運営に声をかけてください。

チーム開発の作法

0. 今日のスタック

開発は85分です。環境構築とビルドに時間を使わない構成を選んでください。

今日のおすすめサークルの通常開発
フロント素の HTML + CSS + JavaScriptNext.js
バックエンドなし(ブラウザだけで完結)自由(Go / Python / Node など)
データ保存localStorage(ブラウザ内)DB
ビルドなし。index.html をブラウザで開くだけあり

今日 Next.js を立ち上げると、環境構築・ビルド・デプロイで開発時間の半分が消えます。素の HTML/CSS/JS なら、Claude Code が書いた瞬間にブラウザで開いて動きます。今日の目的は「AIに指示して動くものができた」の体験なので、そこに時間を使ってください。

チーム全員が Next.js に慣れている場合は使ってOKその場合、下の「機能で分ける」考え方はそのまま使えます。app/ 配下をページ / コンポーネント単位で分担してください。ただし環境構築で15分以上溶けたら素のHTMLに切り替えると最初に決めておくのがおすすめです。
外部APIを使うならAPIキーが必要なAPIは、フロントエンドだけでは安全に使えません(APIと課金タブ参照)。今日はキーの要らない公開APIを選ぶか、外部APIを使わない構成にしてください。

1. Git と GitHub のしくみ

4人で1つのものを作るので、コードを共有する仕組みが要ります。それが Git と GitHub です。

💻 手元(ローカル)= 自分のPCの中
  • ファイルを編集する場所
  • commit で変更を履歴に記録
  • ここだけでは誰にも見えない
GIT push → ← clone / pull
☁️ GitHub(リモート)= チーム共有の置き場
  • 全員の変更が集まる場所
  • ここにあるものが「チームの正」
  • 他の人はここ経由で受け取る

覚える操作は4つだけです。

操作いつ何が起きるか
clone最初の1回だけGitHub にあるものを手元にまるごとコピーする
pull作業を始める前に必ず他の人が push した変更を手元に取り込む
commit区切りがついたら手元の変更を履歴に記録する(まだ誰にも共有されない)
push記録したら手元の履歴を GitHub へ送る = チームに共有される
いちばん誤解されるところcommit は「手元のセーブ」です。push して初めてチームに届きます。 逆に、他の人の変更は pull しないと手元には来ません。「共有されているつもり」で作業を続けるのが、コンフリクトが大きく育つ一番の原因です。
リポジトリの用意と招待は、各チームの上級生がやりますGitHub でのリポジトリ作成・メンバー招待・最初の雛形 push は上級生に任せてください。招待が届いたら承諾して、clone するところから参加します。

push には GitHub の認証が必要です。ここは初めてだとほぼ確実に一度は詰まるところなので、聞かれたり弾かれたりしたら自分で調べずに上級生を呼んでください。10分粘って直らなければ、その人はペア相手のマシンで作業します — 認証の解決に開発時間を使うのが一番もったいないです。
上級生向け:認証がまだの人の最短ルートGitHub CLI が入っていれば gh auth login が最短です(ブラウザにコードを入力するだけで、トークンのコピペが要りません)。gh が無い場合、当日は SSH 鍵を作るより HTTPS + Personal Access Token のほうが速いことが多いです。あわせて git config --global user.name / user.email が設定済みかも確認してください(未設定だと最初の commit で止まります)。
いずれにせよ10分を超えたら、ペア相手のマシンに寄せる判断を優先してください。

コンフリクトしない作法

4人で同じリポジトリを触ると、必ず「他の人の変更と衝突した」が起きます。衝突を上手に直す方法ではなく、そもそも衝突しない配置にする方法をまとめます。

2. 2人1組 × 2台で、担当は「機能」で切る

1人が Claude Code に指示を出し、もう1人が結果を見て次の指示を考える。初めてなら4人バラバラより速く、学びも大きいです。

担当は機能で分けます。「HTML担当・CSS担当」のようなレイヤーでは分けません。

✗ レイヤーで分ける✓ 機能で分ける
ペアA: HTML
ペアB: CSS + JS		ペアA: 投稿ボタン(HTML+CSS+JS 全部)
ペアB: 一覧表示(HTML+CSS+JS 全部)

レイヤーで分けると、HTMLができるまでCSSが書けず、お互いの完成待ちになります。機能で分ければ、それぞれが最後まで動くものを作れます。Claude Code も「投稿ボタンを作って」の1発でHTML/CSS/JSを横断して書いてくれるので、そのほうが自然です。

3. 最初の5分は1人だけが動く

空のリポジトリに全員が同時に push すると即事故ります。ここは上級生が先に済ませてくれているはずなので、その場合は clone から始めてください。

  1. 1人が雛形を作って push — 機能ごとにファイルを分けておくのがポイント
  2. index.html に機能ごとの差し込み口を先に確定させる — これで以降 index.html を誰も触らずに済みます
  3. 全員が clone してから分担開始
index.html                         ← 器。差し込み口を置いたら以降さわらない
features/post.js   + post.css      ← ペアA
features/list.js   + list.css      ← ペアB
<div id="post"></div>
<div id="list"></div>

各ペアは自分のJSからこの差し込み口に描画するだけになります。

4. Claude Code に担当外を触らせない

ここが今日いちばん効くポイントClaude Code は放っておくと関係ないファイルまで整形・リファクタします。つまりAIが勝手に他の人の担当ファイルを書き換えてコンフリクトを作ります。

毎回、触ってよいファイルを明示してください。

features/post.js と post.css だけを変更してください。
他のファイルは読んでも構いませんが、編集はしないでください。

1回の指示は小さく。 大きな指示で複数ファイルを一気に書き換えさせるほど、衝突する面積が広がります。

チームの約束は CLAUDE.md に書く。 リポジトリ直下に置くと、チーム全員の Claude Code が同じ前提で動きます。

# チームの約束
- 素の HTML / CSS / JavaScript で作る。フレームワークは使わない
- 担当: ペアA=features/post.* / ペアB=features/list.*
- 担当外のファイルは編集しない
- index.html は変更しない(差し込み口は確定済み)
- CSSのクラス名は機能名をプレフィックスにする(post-btn など)

5. 小さく、頻繁に

15分に1回は push。溜めるほど解決が大変になります。

git pull --rebase              # 作業を始める前に必ず
# ...作業...
git add -A && git commit -m "投稿ボタンを追加"
git push

6. 詰まったら「直す」より「やり直す」

時間が限られているので、解決に5分かかりそうなコンフリクトは潔く捨てます。

git merge --abort                  # とりあえず元に戻す
git checkout --theirs index.html   # 相手の版を採用

そのうえで自分の変更内容を Claude Code にもう一度やらせる。手で直すより速いです。

まとめ
  • スタック — 素の HTML / CSS / JS。ビルドなし。データは localStorage
  • Git — commit は手元のセーブ、push で初めて共有。作業前に必ず pull。認証で詰まったら上級生へ
  • 組み方 — 2人1組 × 2台。担当は「機能」で切る(HTML担当・CSS担当にしない)
  • 最初の5分 — 1人が雛形を push → index.html に差し込み口を確定 → 全員 clone
  • Claude Code — 「このファイルだけ変更して。他は編集しないで」を毎回言う。指示は小さく。約束は CLAUDE.md に書く
  • 動かし方 — 作業前に git pull --rebase、15分に1回 push
  • 詰まったら — 5分で直らないコンフリクトは捨てて、Claude Code にやり直させる
